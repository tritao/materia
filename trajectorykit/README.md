# TrajectoryKit

`trajectory_core` evaluates bounded joint polynomials, validates their limits and
continuity, and owns immutable execution plans. It has no planner or third-party
native dependencies. MotionKit produces trajectories using Ruckig, TOPP-RA,
Descartes and OPW, then registers them with this shared core. RobotKit executes
those trajectories through the same evaluator and validator.

```
MotionKit planners -> trajectory_core <- RobotKit runtime
```

Configure RobotKit alone to build its runtime and device tests without any planner:

```sh
cmake -S robotkit -B /tmp/robotkit-native -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build /tmp/robotkit-native
ctest --test-dir /tmp/robotkit-native --output-on-failure
```

The `TrajectoryCore` HXI owns the shared ABI records, trajectory and plan handles,
and core calls. `MotionKitNative` depends on that interface and declares only
planner calls. Haxeon loads each set of functions from its owning library on every
platform; handles retain their owning library's destruction function.

Regenerate and audit both interfaces after changing the C ABI:

```sh
trajectorykit/native/tools/check-hxi.sh
motionkit/native/tools/check-hxi.sh
```

The native runtime tests use polynomial fixtures generated by the current pinned
planner. To regenerate them, build `motionkit_runtime_fixtures` in a MotionKit
native build and redirect its output to
`robotkit/runtime/tests/runtime_trajectory_fixtures.hpp`. The fixtures retain the
planner's exact nanosecond knots and coefficients while keeping runtime and device
builds independent of the planner toolchain.

`trajectory_merge.hpp` exposes the shared quintic merge to C++ callers. A
`PolynomialSource` borrows strided coefficient rows from either compact planner
storage or runtime segment arrays; `PolynomialOutput` writes to caller-owned
storage and identifies the source range replaced by each result. The algorithm
keeps the planner's longest-first search and velocity/acceleration plateau rule,
checks candidate extrema at stationary points, and retains the sampled fit check
against the originals. Device conversion additionally checks against the original
motion at the step-clock interval. The existing MotionKit C entry point is a thin
wrapper; runtime merging needs no MotionKit objects or planner library.

The shared merge corpus runs against compact storage in `trajectory_core_merge`
and RobotKit arrays in `robotkit_device_compiler6`. MotionKit's path tests retain
its timed-path plateau regression. The existing shaped-path sliver policy is
explicit in `MergeOptions`; device compilation disables that policy and keeps its
own clock validation.
