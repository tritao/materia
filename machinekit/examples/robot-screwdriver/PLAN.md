# Robot screwdriver plan

Goal: a robot that drives the screws of an assembly, with the screws, the
threaded holes and the screwdriving equipment all coming from the CAD, and a
simulated screwdriver that shares one interface with a real tightening
controller. Threads become real model data on faces, and the editor draws them
as cosmetic threads.

It follows the robot welder's shape (`../robot-welder/PLAN.md`): the work is
found in the CAD, the tool is declared through capabilities, a deterministic
process model runs in simulation, a `ProcessDevice` boundary is shared by
simulation and hardware, and a mission step drives it.

## Decisions for SD0–SD8 (2026-10-09)

- **Axial compliance is in the tool, not the arm.** The spindle sits on a
  spring-loaded feed slide with a sensed stroke, as on production screwdriving
  units. The arm only makes position moves, and the slide supplies and measures
  the feed force. No force control on the arm in SD0–SD8 (see SD12).
- **The screw is simulated by a process model, not by thread contact.** A
  deterministic torque-angle model decides how the screw advances and seats, as
  `WeldArcModel` decides the arc. The screw is held on the bit and moved
  kinematically along the hole axis by `angle × lead`. MuJoCo never sees a
  thread.
- **Screws are presented, not blown in.** A presenter nest with an escapement
  and a part-present sensor; the bit has a vacuum sleeve that holds the screw,
  reusing the suction pieces. Blow-feed through a tube is later.
- **Threads are face attributes, drawn cosmetically.** A thread is semantic data
  on a named face (holes and shanks alike). Helical geometry is never modelled.
  The editor draws threads as a texture overlay on the face's own triangles (see
  SD2, which takes FreeCAD's thread texture as its reference and avoids its
  bugs).

### Implementation decisions

- **SD0 — Property class owns the fastener's mechanical material.** Screws and
  bolts offer 8.8, 10.9, 12.9 and A2-70 as typed classes; their recipes store
  `propertyClass` and derive material, rather than accepting a second,
  contradictory material input. Other component recipes retain their material
  input. The machine member record drops its duplicate material field: recipes
  already supply material, including overrides on other components. Defaults
  remain 12.9 for cap screws and 8.8 for hex bolts.
- **SD0 — Published table values retain their limits.** The tightening catalog
  records Optimas's [steel table](https://optimas.com/technical-resources/pre-load-and-tightening-torques-of-metric-thread-steel-fasteners/)
  at friction 0.125 and [A2-70 table](https://international.optimas.com/technical-resources/stainless-steel-fasteners-pre-load-and-tightening-torques/)
  at friction 0.1, with torque in Nm and preload in N. These are published
  maximum assembly guidance values, not a validated joint process program.
  Only the catalog's M3–M20 coarse sizes are included; unsupported fine pitches,
  hands, starts and custom dimensions report a missing row instead of
  interpolation. Fine thread designations still derive from custom screw specs.
- **SD0 — CAD thread values belong in CadKit.** MachineKit fasteners and lead screws
  share `cadkit.threads.ThreadSpec`; metric, trapezoidal, Acme and ball-race
  profiles retain their distinct meaning. Ball races have no cosmetic flank
  profile. A function-only `ScrewFastener` interface shares driven-fastener
  facts without haxeon's class-to-typedef structural assignment.

- **SD1 — Face names own thread identity.** Immutable `ThreadedFace` attributes
  travel with Haxe shapes. Copying and naming remap them by topology index;
  operations retain source-face handles and follow exact native history identity
  when a face splits. Only proved deletion removes an attribute. Missing or
  ambiguous references report the face name; dimensions never repair a reference.
  The start binds once in the surface's native axial parameters. Each query clips
  that interval against bounds measured in the actual face-axis frame and derives
  the visible frame again. This handles rotated faces and oblique end cuts without
  relying on tessellation or world-axis bounds. Manufacturing mirrors retain the
  specified hand: the attribute declares the thread to cut on the mirrored body.
- **SD1 — Threaded bores share semantic data, not helical geometry.** Tapped
  features cut their authored tap drill and carry a separately editable thread
  depth. Plain, recessed and tapped styles are exclusive. Component tap tools,
  nuts and lead screws use the same attributes; custom nuts require an explicit
  thread instead of guessing a pitch. Existing component envelopes remain exact.
  Saved holes include nominal thread data and depth; the document format advances
  from v12 to v13, with the two empty BIM examples regenerated by the current encoder.
  The original SD0 implementation advanced MachineAssembly v13 to v14. After rebasing
  onto main's v17 format, dropping the saved duplicate member material advances it
  again to v18.

- **SD2 — Portable wire facts belong in ProjectKit.** The immutable CAD value
  remains `cadkit.threads.ThreadSpec`; its wire data and hand/profile enums live
  once in ProjectKit, avoiding a reverse dependency on the B-rep. Wire IDs stay
  identical. The original SD2 implementation advanced SceneArtifact v18 to v19.
  Rebasing onto main's v27 format and adding the thread packet advances the current
  format to v28 (before the SD4 v29 extension); older versions are rejected.
  Each part carries freshly derived named intervals beside its exact tessellation;
  frame and length use the part unit, while nominal dimensions remain millimetres.
  Robot tools and mission semantics are unchanged.
- **SD2 — Overlays share geometry and lifecycle with their part.** A
  `CadGeometryData` owns both the base streams and their semantic display packets.
  The overlay clips those streams, creates identity children and applies the same
  runtime pose and highlight. Structural deletion stages those children in the
  existing atomic edit; textures are released only after the commit. Analytic
  profile tiles include eight normalized mip levels; the existing shader suffices.
  Interior boundaries draw stroke rings, including a partly threaded shank's
  transition to its plain segment. Ball races omit the flank overlay.

- **SD3 — Connections are rebuilt from current CAD.** Fixed head seats select
  the screw and clamped occurrence. Clearance faces are queried geometrically;
  internal threads still resolve only by their strong topological names. Face
  intervals give engagement, and solid queries give the actual tip and blind
  floor. Intervening plain bores or solids produce diagnostics, rather than a
  connection to a farther threaded part. Names combine occurrence paths and face
  names with length prefixes; no axis, length or fastening cache is saved.
- **SD3 — Qualified joint limits are authored, never inferred from torque.**
  `FastenedAssembly.join` supplies optional minimum engagement and an angle
  window in radians from snug. The angle window stays absent until the engineer
  supplies qualified limits: a published torque/preload table cannot derive it.
  These are code-authored workpiece policies, like `Weldment.join`, not a new
  saved machine or scene format. Unknown threaded materials require an explicit
  minimum. The existing NEMA design's 1.3 d minimum and 0.5 mm tip clearance
  move into `NemaMountPlate`, without changing its geometry or screw size.
  Standard nut height may likewise be an explicit joint minimum; the conservative
  steel default remains 1 d.

- **SD4 — Equipment ratings are explicit design assumptions.** The custom spindle
  has a 20 Nm capacity, a 600 rpm speed limit, 20 mm of feed and a 2 N/mm
  spring rate. These are authored equipment inputs, not vendor ratings or new
  tightening-table values. The feed is a bounded prismatic joint with an absolute
  linear scale; the spindle is a continuous revolute joint. Spring rate travels
  with the capability; SD5 uses it to calculate feed force in the process model.
  The tool cable carries separate electrical power and signal services in the
  port graph. The carrier declares its fitted bit and its scoped joint/encoder names. Channels
  derive from that capability, without looking for similarly sized components.
- **SD4 — The preview stops at equipment.** Four seated SD3 screws and a
  hand-loaded presenter remain CAD members. The cell checks each fastening's
  drive and torque capacity, on-axis reach at the socket and at 10 mm intervals
  out to the 40 mm approach, and exact solid clearance at the approach samples.
  The existing design-only axis reach solver is shared with welding without
  changing its math. Hex-socket bit tips use their nominal across-flats profile;
  other symbolic drives retain an explicitly documented preview envelope.
- **SD4 — Scene tool data identifies real motion.** SceneArtifact advances to
  v29 and rejects v28. A screwdriver packet carries bit identity, capacities,
  stroke and spring rate, four channels and the real feed/spindle/encoder IDs;
  validation requires those joints on the contact chain and matching feed travel,
  converting the assembly length unit to mm before comparing the stated stroke.
  Start and reverse stop on every stop; vacuum follows the suction holding policy
  through a commanded stop. The app declares the channels and loads the equipment
  on both backends. The process observer and sensor contract remain SD5, so the
  equipment is not silently treated as a suction tool or given a fabricated sensor.

- **SD5 — Programs require qualified joint inputs.** `TighteningPrograms` lives
  in MachineKit's process package, where ProcessKit is already a dependency.
  It derives target torque and qualified angles from the current fastening;
  speeds, stroke windows, torque limits and run-down watchdog are explicit policy.
  Joint stiffness, prevailing torque, strip threshold and lead-in tolerance are
  explicit simulation inputs, never inferred from the torque/preload table.
  The equipment cell has no qualified angle window and therefore starts with an
  idle, unconfigured observer. Starting an unqualified slot names the missing slot.
- **SD5 — Sensor units and process ownership are shared.** RobotKit owns the
  seven-value contract (Nm, radians, rad/s, mm, phase, result, sealed vacuum flag);
  ProcessKit generates the Rust layout from it. Joint stiffness is Nm/radian.
  Model thresholds resolve in order even when a sample crosses several of them.
  The model returns a requested spindle rate; the observer publishes measured
  shaft speed and follows measured rotation while reversing.
  Feed and spindle use the existing native process-ownership bits; a narrow
  tick-path API drives only those coordinates and preserves arm commands.
  The live callback supplies separate starting head and body poses plus the
  thread lead-in point, so runtime screw advance never becomes the next starting
  pose. Reverse unloads elastic rotation before axial withdrawal; a new tightening
  cycle after reversal requires explicit reconfiguration. No saved schema changes.

- **SD6 — Pickup preserves the actual body/socket calibration.** The observer
  computes the identified screw's live socket from its actual collision-body pose
  and the separately supplied CAD head/body frames. During transfer, native
  holding carries it on the bit; the distant work frame cannot pull it out of
  the presenter. The thread constraint begins only within the live lead-in and
  retains the actual contact offset. Measured axial offset changes run-down
  travel so the CAD seat stays fixed, rather than snapping the screw to its
  nominal start. Physical presenter fixtures support their screws before sealing.
- **SD6 — Arm motion excludes the process coordinates.** A derived planning TCP
  at the uncompressed bit is mounted on the feed's parent. Its chain excludes
  both named process joints; the real runtime TCP remains on the spindle.
  The runner follows measured compression near the qualified stroke midpoint,
  rather than deriving arm advance from cycle angle (which includes slipping
  and elastic rotation). It stops the spindle, waits for measured rotation to
  cease, then releases vacuum and retracts. Failed tightening retains vacuum
  for the recovery step; result records preserve measured cycle angle explicitly.
  The simulated endpoint declares a 16-double-epsilon observation precision: a
  MuJoCo feed at its zero stop otherwise faults on roundoff near 1e-20 m and
  releases vacuum. Authored overtravel and commanded limits remain unchanged.
- **SD6 — Saved screw missions share the qualified program boundary.** ProjectKit
  owns the wire settings and validates them for both scene missions and live
  ProcessKit programs. SceneArtifact v30 rejects v29 and carries the identified
  screw, presenter sensor, threaded occurrence and exact topological face name.
  Socket, pickup, entry, seat and hole frames use metres; lead and feed windows
  use millimetres. Validation compares the hole frame, lead and hand with that
  occurrence's exact named thread packet and requires its presenter's declared
  presence sensor. An equal bore cannot repair a missing or ambiguous reference.
- **SD6 — Released screws belong to their actual fixture.** An OK release
  transfers the native body to the exact threaded occurrence, preserving its
  measured pose. Both robot-link fixtures and independent environment fixtures
  carry it when they move. Failed tightening keeps vacuum for recovery.
- **SD6 — Collision pieces preserve openings in generated previews.** Socket,
  shank, bit and presenter pieces are authored with their component geometry.
  Generated previews have no editable CAD session, so their already-centred
  pieces also pass through the canonical assembly collision boundary. A session
  compound copies its convex pieces into one body; presence and ray queries use
  the pieces, and the deterministic backend resolves their transformed OBBs
  separately. It still approximates each convex piece by its local box. The
  presenter's conservative supports stay outside its circular bore. Only the
  declared bit carrier and its identified, kinematically held screw exclude
  mutual native contact; presenter and workpiece contacts remain enabled.
- **SD6 — The drive-one example qualifies M6 explicitly.** Bearing 6003 gives
  the M6 connection; the original 608 equipment preview remains M5. The new
  example authors its process limits and 0.05 mm across-flats bit clearance.
  Nominal drive identity and the published 16.5 Nm target remain separate from
  that fit allowance. The actual socket datum and measured solid tip derive
  entry and seat; lateral seat offset must stay inside the authored 0.5 mm
  lead-in window. Initial arm roll matches the socket before the first move.


- **SD7 — Replacement supply and rejection are portable facts.** SceneArtifact
  v31 rejects v30. Each job may declare one separately identified replacement
  screw, its presenter and scoped presence sensor, and a reject pose relative
  to an exact bin member. Validation requires the replacement's exact component
  definition, not similar dimensions. Derived replacement jobs retain the one
  qualified connection and change only supply identity and pickup. The generator
  reserves both primary and replacement bodies across the whole assembly.
- **SD7 — Travel accommodates the measured spindle phase.** Each attempt
  derives its free-bit planning frame from the measured shaft coordinate. The
  whole-cell adapter uses collision-planned joint travel between approaches,
  then axial Cartesian contact and withdrawal. Linear transfers accumulated
  wrist compensation until the fourth cycle hit its wrist limit; joint travel
  can choose a bounded equivalent wrist pose. Planning retains measured process
  coordinates outside the six arm DOFs. Its live cell geometry retains compound
  pieces instead of also adding their filled enclosing box. Drive-one retains
  its established Cartesian sequence.
- **SD7 — Recovery consumes live stop and release feedback.** The failed result
  keeps its original measured angle; reversal starts from the fresh stopped
  angle, including physical coast. Allowed sample variation derives from the
  stop-speed threshold times the sample duration plus angular resolution.
  Observer feedback follows the actual shaft and held-body state through stopped
  reversal and vacuum release, instead of latching the process result's angle
  or the last reversing frame's vacuum.

- **SD7 — Transport loss stops the arm before recovery.** A process NOK does
  not fabricate a manipulator fault. The controlled stop discards queued motion,
  preserves existing faults and waits for confirmed rest before publishing the
  failed attempt. A lost body is neither reversed nor reported as rejected.
  Its retreat is collision-planned from the measured stopped pose. Only the
  identified spindle body, lost screw and named contact fixtures receive escape
  clearance; normal 5 mm clearance is required again at the retreat endpoint.
  Withdrawal retains measured tool orientation until the bit is clear, with
  inverse-kinematic samples and every connecting joint edge checked. Normal
  joint travel changes orientation only after withdrawal. A random joint-space
  search inside the socket was prohibitively slow; the constrained withdrawal
  keeps its search bounded without weakening the collision proof. Contact
  fixtures retain their CAD rigid/adjacent collision rules. If a loose
  screw settles inside the usual 0.5 mm contact margin, the escape preserves
  at least half its measured positive gap along every checked edge. Overlap or
  another blocked pair causes a bounded clearance wait and a named failure.

- **SD7 — Endpoint access uses the actual CAD solids.** Whole-cell generation
  checks primary and replacement pickup/lift, thread entry and head seat with
  the qualified feed compression, and rejection. Samples follow the authored
  approach distance. Full socket orientation includes roll and stays inside
  arm joint limits; the original free-axis solver retains its old tolerance.
  CAD booleans check the arm/tool against the cell, the tool against nonadjacent
  arm members, and the held fastener against the cell and non-carrier arm parts.
  Only CAD rigid/adjacent relations and the qualified fastener/threaded-member
  engagement are intended contacts. The active fastener is staged, so its
  display seat and occupied presenter template are not duplicated obstacles;
  other seated heads and supplies remain a conservative occupancy check.
  Every check restores the initial arm and feed coordinates and releases its
  owned geometry, including when access fails.

- **SD7 — Final passes retain engaged joint state.** `TighteningModel.retighten`
  copies a successfully seated model into an independent continuation. It
  preserves measured contact travel, original snug angle, cumulative rotation
  and preload; the newly qualified higher target cannot change the thread or
  joint response. Start rechecks measured vacuum, alignment and feed force.
  Final angle limits remain relative to the original snug point, and reversal
  unloads the retained elastic rotation before backing out the full thread
  engagement. The simulation/mission binding must retain this state only for
  the exact successfully released body and fastening; resetting an empty model
  between passes is not a valid implementation.

- **SD7 — Final motion acquires the installed socket directly.** A
  `ScrewPlan.finalContact` carries the measured socket and retained advancement.
  The runner approaches it without a presenter trip, seals vacuum, compresses
  the feed and only then starts tightening. It derives the following/recovery
  origin by backing out the retained advance along this live socket axis, so
  actual contact calibration and roll remain intact. Retraction and reversal
  follow that same reference. Vacuum loss during final engagement uses the
  existing controlled arm stop and retains the cumulative failure angle.

- **SD7 — A retained simulation joint belongs to one released body.** The
  observer records successful fixture transfer against the exact fastening,
  threaded member, named face, body and thread hand. Selection consumes that
  state; a failed continuation cannot restore an earlier OK. Final setup
  returns the live body's socket and calibrated advancement while keeping its
  anchor inactive until vacuum reacquires the body. Recontact verifies the
  intrinsic socket/lead-in geometry and actual seated pose against that retained
  engagement. The fixture instance must also be the original release fixture:
  different CAD members can share a native rigid parent, so native ownership
  alone cannot reidentify the threaded member. Reset/rebuild discards every
  retained entry. Final shaft angle
  uses a fresh measured origin plus the retained cumulative joint angle, so
  stopping coast does not discard preload or add invented thread travel.
- **SD7 — The replacement budget spans passes.** `DriveFastening` accepts one
  or two remaining attempts; the existing default is two. A final run after a
  snug replacement must allow only its installed-body attempt, recover its NOK
  and report exhaustion without asking for a third supply. The staged mission
  coordinator must derive this limit from the preceding measured snug report.
- **SD7 — Snug stops at the measured head seat.** `TighteningProgram.stopAtSeat`
  preserves the final program qualification and stops at the calibrated snug
  angle with prevailing torque, even if a sample crosses later thresholds.
  Lead-in, run-down torque, feed-force and run-down watchdog failures still
  apply; a strip threshold at or below prevailing torque cannot produce a
  successful seat stop. A continuation requires a final program. This does not introduce a
  lower catalog torque or reinterpret a snug OK as final tightening.

- **SD7 — Staged missions store each qualified job once.** SceneArtifact v32
  rejects v31. Wire invocations are `Single(job)`, `Snug(job, slot)` and
  `Final(fastening)` with explicit variant IDs. Final resolves the unique
  preceding snug definition; geometry, final qualification and supplies are
  not copied into a second saved job. The mission envelope encodes these
  invocations through the generated wire codec, and the old plain-job decoder
  is removed. Validation rejects reused jobs/supplies, missing or repeated
  finals, out-of-order snug passes and equal/invalid stage slots.
- **SD7 — Stage reports preserve measurements and actual supply use.** Every
  snug/final run records its pass and measured attempts. Final starts with the
  preceding successful report's exact `installed()` identity and has
  `3 - snug.attempts.length` attempts remaining. Its first attempt recontacts
  retained engagement; an unused reserve, when permitted, starts a fresh full
  final cycle. An exhausted snug produces an explicitly skipped final with a
  reason and no tightening measurement. Controller/recovery faults stop the
  mission and cannot become a skipped or measured successful final.

- **SD8 — Protocol enable and measured process feedback are separate.** The
  Open Protocol client implements the commissioned single-station revision-1
  profile from Atlas Copco's published
  [specification 2.16.0](https://asutp.org/Atlas_Copco/OpenProtocol_Specification_R_2.16.0.pdf).
  MID 0043 unlocks the tool; it does not start tightening. Start, reverse and
  vacuum require commissioned machine I/O. MID 0061 supplies measured torque
  and a reported angle, not live speed, feed stroke or a guaranteed cumulative
  spindle datum. Its NOK remains unclassified; no cross-thread or stripped
  result is inferred from that bit. Hardware feedback must supply the canonical
  seven measured values independently, with the engagement angle datum.
  This profile does not negotiate revisions or claim support for MTFocus6000:
  its [2026 controller appendix](https://servaid.atlascopco.com/AssertWeb/cs/AtlasCopco/Document/28551388/DownloadConvertedFileAsPdf)
  requires communication-start revision 6.
- **SD8 — Acquisition freshness belongs to the source.** The discrete profile
  commissions program codes, LSB-first pins, reverse/start semantics and the
  acquisition clock and maximum age. Readiness requires the acquired program
  echo to match the commissioned code; a ready bit alone cannot acknowledge
  selection. Its I/O supplies one atomic digital and
  measured-value snapshot, source sequence and acquisition timestamp. Polling
  a repeated snapshot cannot refresh it; conflicting repeats, wrong clocks,
  future times, backwards sequences and stale measurements stop drive and
  reverse while retaining vacuum. OK/NOK inputs must agree with the measured
  result and complete phase. Link/acquisition faults latch. The common process
  device optionally consults this controller readiness and fault boundary;
  the established simulated device behavior stays unchanged.

- **SD8 — The virtual nutrunner acquires the existing CAD plant.** One Haxe
  torque-angle plant follows physical feed/spindle snapshots and the executed
  RKD6 outputs. Rust captures its seven measured values atomically, with the
  actual acquisition sequence and device time; repeated UART publication cannot
  refresh an acquisition. The native ADC guard stops active drive on missing or
  stale measurements. Virtual counters use the loaded CAD joint origin rather
  than applying physical encoder offsets again.
- **SD8 — Independent outputs cross the device boundary.** Generated wire
  revision 15 adds a typed, session/sequence-qualified controller output record.
  Path events and independent controller writes share the declared channel
  kinds and STOP safety policy. A controller write supersedes that channel's
  scheduled HOLD/resume latch, including a write of the same value; arm HOLD
  preserves these independent outputs. Faults and e-stop still enforce safe
  values, and active process outputs retain their link lease after arm STOP.
  The current schema lock is regenerated without migrations; saved scene
  formats and existing native ABI layouts do not change.

## What exists

- Fasteners in `machinekit.standard`: `SocketHeadCapScrew` (ISO 4762),
  `HexBolt` (ISO 4017), `HexNut`, `FlatWasher`. Specs carry diameter, pitch,
  head and socket sizes, thread length, tap drill, ISO 273 clearances and
  DIN 974-1 counterbores; screws expose `head` and `tip` connectors and
  clearance/tap/counterbore cutters. Threads are semantic only. There is no
  drive type, no property-class mechanics and no tightening torque.
- `LeadScrewThread` (`machinekit/motion`) has diameter, pitch, starts and hand.
- Assemblies seat screws with a `fixed` mate from a frame on the clamped part
  to the screw's `head` (`FlangeBearingAssembly` `screw$i-seat`, also
  `MotorShaftBearings`). `FlangeBearingAssembly` already sizes screws for 1.5 d
  engagement and exposes `screw<i>Tip`. Which part the screw threads into is
  implicit: there is no fastening relation.
- CadKit: `HoleFeature` (plain, counterbore, countersink; blind or through)
  names its bore body `"bore"` for topological naming, but has no thread data.
  `Shape.faceAxis()` gives a cylinder/cone face's axis and radius, and
  `GeometricConnectors` turns faces into frames.
- Tool plumbing from welding and machine tending: `ArmTool`,
  `EndEffectorControls`, `RobotScene.robotTools`, cadbridge
  `EndEffectorControlBinding`/`EndEffectorRuntimeBridge`, `ToolChannels`,
  `SimulatedSuctionTool` (holds an object on a link), process-driven tool
  joints (`rk_simulation_velocity_drive`, the bench mill's spindle, with an
  effort cap), `PortKind` `Vacuum`/`Pneumatic`/`ElectricalPower`/`Signal`.
- ProcessKit: `ProcessDevice`, `ProcessEngagement`, `ProcessRun`, the welder's
  outputs/feedback split, `WeldContract` and its Rust generator, the Modbus
  client, and the bounded guarded move of `ContactSearch`.
- Rendering: SceneKit has one PBR material per node with base-colour and normal
  textures, `REPEAT` samplers, and `TEXCOORD0` streams. CAD tessellation keeps
  each face's triangle range (`cad_mesh_face_range`), and the face-hover
  overlay (`ScenePresentation.ensureFaceHover`) already draws one face's own
  triangles in a child node with its own material. Tessellation does not export
  UVs, and there is no per-face material.

Missing: thread data on faces, the fastening relation, a screwdriver tool kind,
a tightening model, a screw mission step, screw feeding, an Open Protocol
client, and any thread rendering.

## Steps

**SD0. Fastener data.**
- A `ScrewDrive` enum (hex socket, hexalobular, cross, hex head, slot) with its
  size, so the bit is chosen from the screw. SHCS: hex socket of `socketSize`;
  hex bolt: hex head of `acrossFlats`.
- `PropertyClass` (8.8, 10.9, 12.9, A2-70, …) on screws and bolts, replacing the
  free-text `material` default. Class determines material; recipes have no second
  material input. Defaults stay 12.9 for cap screws and 8.8 for hex bolts.
- A tightening table: assembly torque and preload per size and property class
  at a stated friction coefficient, with its source recorded like the existing
  catalog sources. No numbers are invented: they come from a cited table.
- A `ThreadSpec` value type: designation (`M6`, `M6x0.75`), major diameter,
  pitch, starts, hand, internal/external, tolerance class. Metric coarse and
  fine come from the existing specs; `LeadScrewThread` yields a `ThreadSpec`
  (trapezoidal), so lead screws join the same scheme.
- Checks: every catalog screw has a drive, a thread spec and a torque for its
  default class; `LeadScrewThread`'s lead equals `ThreadSpec` pitch × starts.
  Class survives recipe and saved-assembly round trips; contradictory material
  overrides and unsupported tightening rows are reported.
  Recipe changes advance the machine format from v13 to v14 and the CadKit
  document from v11 to v12; the two empty BIM examples are regenerated with the
  current encoder. Existing geometry, default materials and mass stay unchanged.

**SD1. Threads on faces.**
A thread is attached to a named cylindrical (or conical) face, never found again
by matching radii.
- `ThreadedFace`: face name, `ThreadSpec`, start (the face end the thread begins
  at) and length (full face or a stated depth).
- `HoleFeature` gains a tapped style: the bore is cut at the tap drill and the
  bore face carries an internal `ThreadSpec` and thread depth. `tapHole()` on
  the fastener components uses it.
- Screw and bolt shanks carry an external `ThreadSpec` over `threadLength` from
  the tip, so a partly threaded ISO 4762 screw shows its plain shank.
- `Threads.of(part)` returns each threaded face with its axis frame from
  `Shape.faceAxis()` of that face: origin at the thread start, +Z into the
  material for internal threads and toward the tip for external ones.
- Through-holes, counterbores and countersinks keep working; a counterbored
  tapped hole is not a thing (rejected). Saved thread inputs use the current v13
  document format; face intervals and frames are rebuilt, never serialized caches.
- Checks: a tapped M6 hole's thread axis and depth; editing the hole position
  keeps the thread on the same named face; two equal tapped holes keep their
  own threads (the case FreeCAD #30005 got wrong); a part with an unthreaded
  hole of the same diameter as a threaded one shows no thread there.

**SD2. Cosmetic threads in the editor.**
Reference: FreeCAD PR #22573 "PartDesign: thread texture" (merged 2026-03),
fixes #28461 and #30005, open #24072 (thread-end ring). FreeCAD re-triangulates
the bore faces and lays a hand-drawn translucent PNG over them with UVs
u = angle / 2π, v = axial distance / pitch, a clip plane at thread depth, a
mirrored U for left hand, and a per-hole hash phase. Its overlay lives outside
the model and found its faces by radius and axis, which caused both fixes.

Here:
- **Bound to the model.** The overlay is built from `Threads.of(part)` (SD1):
  the face comes by name and the axis from the face itself, not from a sketch
  or a radius search.
- **Same triangles as the face.** The overlay mesh is the face's own triangle
  range (`subelementGeometry(faceIndex)`), like face hover, so depths match the
  base mesh exactly and there is no z-fighting. It lives in a child node of the
  part's runtime node and follows pose overrides as hover does.
- **UVs in Haxe.** u = angle around the thread axis / 2π × starts, mirrored for
  left hand; v = axial distance from the thread start / pitch. Triangles that
  cross the seam get duplicated vertices: unwrap the angle by one turn before
  multiplying by starts, then mirror for hand. Clip triangles at both interval
  ends, retaining every untouched source position exactly.
- **A generated texture, not a drawing.** A small tileable normal map from the
  60° (or trapezoidal 30°) profile, plus a base-colour texture slightly darker
  at the roots, both mip-mapped with a `REPEAT` sampler. This uses SceneKit's
  existing normal mapping, so no shader change, and works on desktop and web.
  The overlay's material takes the part's appearance (colour, metallic,
  roughness) so a thread looks like the part's own surface.
- **Phase from the name.** Each thread's u offset comes from a stable hash of
  its face name, so overlapping threads (a screw in its hole) look distinct.
- **Thread-end ring.** A cosmetic circle at the end of a partial thread, drawn
  through the existing stroke pass.
- **External threads too.** Screw shanks draw the same overlay facing outward.
- A view setting turns cosmetic threads off.
- Only if the textured look fails close up: a thread mode in
  `scene_fragment.glsl` that draws the profile analytically with `fwidth`
  antialiasing. Not planned unless needed.
- Checks: an unclipped overlay retains the face's triangle count and exact
  source positions; only seam copies and clipped intersections add vertices
  (an equal vertex count would contradict both operations). UVs across the seam
  stay continuous; a 20 mm deep thread in a 30 mm hole stops at 20 mm; left-hand
  threads mirror; a screenshot test of a tapped plate and an M6 screw on the
  desktop and web builds when the web toolchain is available. The desktop
  check opens `materia.threads.project.json`: a sectioned plate has RH 20 mm
  and LH 12 mm threads in equal 30 mm tap drills, a plain equal drill, and
  an M6 screw. Capture the full scene and `--frame=project:plate|project:screw`
  with `app/run-built.sh --perspective --capture-dir=... --capture-seconds=1`.

**SD3. Fastenings from the CAD.**
- `Fastening`: screw (or bolt), clamped member and its clearance hole, threaded
  member and its tapped hole (or a nut), engagement length, `ThreadSpec`,
  tightening spec (torque, angle window), and a name made from the face names,
  so it survives edits like a weld seam.
  Published torque/preload guidance accompanies the connection; the angle window
  is optional qualified input, since CAD and those tables cannot supply it.
- `Fastenings.find(assembly)` derives fastenings from the existing seat mates
  and the threads: the screw's axis runs through a clearance hole in the seated
  part and into a coaxial threaded face of the next part. It reports instead of
  skipping: no threaded face on the axis, thread mismatch (diameter, pitch,
  hand), engagement under the minimum (default 1 d in steel, 1.5 d in
  aluminium), clearance hole smaller than the major diameter, screw too long
  for a blind hole.
  It also checks starts/profile, plain shank entering the thread, ambiguous
  head seats or next threads, and intervening plain bores or solid parts.
  Conical named threads use their actual circular boundaries and axis-frame
  bounds. A nut's through bore permits the tip to extend past its far end.
- `FastenedAssembly` resolves them afresh, with `join` for optional joint-specific
  engagement and qualified angle limits, like `Weldment.join`.
- Workpiece: `FlangeBearingAssembly` on a plate with tapped holes, then a NEMA
  motor on `NemaMountPlate` (four M3).
  `materia.fastenings.project.json` exposes both CAD previews, with no equipment
  or start-page change. The canonical NEMA plate is extracted from
  `MotorShaftBearings`; tapped motor mount faces gain attributes without changing
  their tap-drill solids or names.
- Checks: the flange assembly gives four fastenings with the right engagement;
  shortening a screw reports under-engagement; moving the plate's holes off the
  flange's bolt circle reports no threaded face.
  Also cover reversed head-seat orientation, rotated included workpieces,
  conical blind bores, through nuts, explicit limits, and blocking next parts.

**SD5. Tightening model and simulated screwdriver.**
- `TighteningProgram`: run-down speed, final speed, target torque, angle
  window from snug, torque limits per phase, maximum run-down angle, stroke
  window. Programs come from the fastening's tightening spec.
- `TighteningModel` (pure, deterministic): from the screw's state, the feed
  force (spring rate × stroke) and the spindle angle it gives
  - engagement: the screw starts only if it is on the axis within the hole's
    lead-in and the feed force is in range; otherwise it slips (no advance) or
    cross-threads (torque rise before the expected run-down angle);
  - run-down: advance = angle × lead, prevailing torque;
  - snug: when the head reaches its seat face;
  - final: torque rises with explicit joint stiffness in Nm/radian until the target.
  Outcomes: OK, no screw, no start, cross-thread, stripped (torque drops), early
  high torque, angle out of window, run-down too long, screw lost.
- `ScrewdriverSensor` contract: torque, angle, speed, stroke, phase, result
  code, vacuum, with a Rust contract generated like `weld_contract.rs`.
- `SimulatedScrewdriver`: a step observer on the tool link. It reads the
  channels, computes the stroke from the TCP depth against the screw head, runs
  the model, drives the spindle and slide joints to the model's state, moves the
  held screw, and publishes the sensor frame. Holding reuses
  `SimulatedSuctionTool`'s attach. SD5 installs the app observer factory and
  declares the process sensor; qualified slots are configured explicitly.
- `ScrewdriverProcessDevice` with `ScrewdriverOutputs` (select program, start,
  reverse, vacuum) and `ScrewdriverFeedback` (result, live values).
- Checks: each outcome from a constructed case; an M6 into steel reaches
  target torque within its angle window; a misaligned start reports no start;
  the same inputs give the same trace.

**SD7. Whole assembly.**
- `ScrewdrivingMission.generate`: every fastening into `screw` steps, with
  presenter trips; ordering by pattern (cross order on a bolt circle) and an
  optional two-stage run (all to snug, then all to final); reach and clearance
  diagnostics shaped like `WeldAccess`. Access checks include each identified

- A run report: per-fastening results and failures.
- Checks: the flange assembly's four screws in cross order on both backends; an

**SD8. Real tightening controller.**

### SD12 design: hybrid force/position entry search (2026-10-14)

Geometry it must handle: the screw passes through the flange housing's
clearance bore (first surface about 23 mm below the approach) into the tapped
plate (CAD entry plane about 40 mm below). A registration error puts the first
contact on the flange face, not at the CAD plane.

- **Hybrid control.** The advance axis is force-controlled, the hole plane
  position-controlled.
  - In free space the tool descends at the commissioned approach speed: a
    guarded move.
  - Once contact is confirmed, `CartesianAdmittance` (built in the search frame
    u, v, n) regulates the axial force to the commissioned contact force
    through its `target` wrench.
  - The maximum force and torque are hard stops, never regulators.
  - Lateral motion tracks the search reference and stays compliant through the
    admittance's lateral axes.
- **Search wherever contact happens.** Phases:
  - `Approach`: free descent holding the nominal axis.
  - `Search`: contact held, spiral around the lateral target.
  - `Descend`: through a found hole, laterally compliant, so the bore centres
    the screw.
  - `Seated`: done.
  - `Failed`.

  Transitions:
  - Contact above the CAD entry window starts a `Search` at that surface. When
    the measured depth passes the contact depth by the commissioned entry
    advance, the screw has dropped into a hole and goes to `Descend`.
  - Contact at the CAD plane searches the same way.
  - Reaching the CAD entry plane plus the entry advance (within the depth
    tolerance) is `Seated`, touching or not. That is the tightening handover.
    Whether a thread is really there is the tightening cycle's question: its
    lead-in, stroke and torque checks name a missing or damaged thread.
  - On a searched surface the axis stays force-regulated even through a brief
    load dip, so a slip on a chamfer cannot turn into a plunge.
- **Path-parameterised spiral.** An Archimedean spiral of commissioned radius
  and pitch (radial spacing per turn, chosen against the hole's capture
  radius).
  - Its parameter advances at the commissioned path speed only while the
    surface carries the screw and the measured lateral lag is inside the
    tracking tolerance.
  - The lag is judged net of the deflection the controller deliberately allows.
    Tracking and lateral admittance settle at force / (damping x gain) from the
    reference under a lateral force. Up to the regulated contact force (about
    what a chamfer pushes) that offset is excused, so a hole's chamfer pulling
    the screw towards the hole is not a stall. A wall pressing harder still
    stalls it.
  - There is no clock to catch up with, and no relief retry.
  - A spiral that makes no progress for the commissioned stall time fails with
    its lag, radius and force. Reaching the radius fails as exhausted.
- **Explicit phases.** `ScrewEntryController` is pure: measured TCP position,
  wrench and time in, twist command and phase out. Its transitions are tested
  against a small simulated plant: a point tool with servo lag and sensor
  latency, stacked plates with chamfered holes, contact stiffness and friction.
  That runs in milliseconds and covers:
  - nominal entry;
  - an offset through a clearance bore;
  - a missing hole;
  - an obstruction;
  - the force bound at every step.

  `ForceGuidedScrewEntry` adapts it to `ServoSession`. It builds the controller
  at the measured approach pose and owns the sensor-freshness, clock, travel,
  force/torque and run-time checks, and the stop. The CAD offset-hole
  acceptance on MuJoCo is the final check, not the loop for tuning.
- **Plant results (stiff tool: 2e5 N/m servo and contact, 10 ms sample
  latency).**

  | Case | Time | Peak force |
  | --- | --- | --- |
  | Nominal (seats through the bore without searching) | 20.3 s | 3.2 N |
  | 1.0 mm offset | 23.0 s | 18.9 N |
  | 1.14 mm offset | 24.0 s | 18.8 N |
  | 1.3 mm offset | 25.5 s | 18.6 N |

  - The missing bore and debris in the bore fail by name; a missing tapped hole
    seats and is left to the tightening cycle.
  - With a 2000 N/m feed spring (axial damping 400) between the TCP and the
    screw, the nominal case is unchanged and the offsets seat in 21.7-24.2 s
    with a 10.8 N peak: the spring takes up the chamfer climb before the
    admittance answers.
  - Each offset peak is the screw climbing back out of the bore's chamfer onto
    the flat face. The surface rises as fast as the screw moves sideways, faster
    than an axial admittance damped above contact stiffness x latency can
    retract.
  - Commissioning relations the plant exposed:
    - The tracking gain must keep the compliance lag at the contact force
      inside the tolerance. 10/s is needed; at 25/s a bore wall was pushed to
      227 N.
    - Lower axial damping (2500) or a slower spiral (1 mm/s) cut the peak only
      to about 16.8 N.
- **Profile.**
  - Kept: sensor; age; contact force; contact threshold; per-axis mass and
    damping in search axes; linear and angular speed; step; approach speed;
    force and torque bounds; travel and run bounds; registered region; spiral
    radius, pitch, speed, tracking gain and tolerance; entry advance; stall
    time; confirmation samples.
  - Removed: the target wrench in sensor axes, contact seed offset, contact
    relief, candidate-progress timeout, load-drop threshold, spiral turns,
    duration and overtravel.
  - SceneArtifact bumps its version. Old artifacts are rejected.
- **Simulated reaction path.** A contact force only matters if it pushes back on
  the tool. While the arm owns axial motion:
  - the screwdriver's feed slide is what it is mechanically, a spring of the
    commissioned rate resting extended and critically damped over the feed
    mass (`rk_simulation_spring_process_joint`), rather than a position-held
    stroke;
  - the held screw is a rigid physical child of the bit link (a fixed object
    joint) instead of a kinematic body placed each tick. A kinematic screw
    reported the 1 mm offset's flange contact as 229 N that never reached the
    feed or the arm.

  `SimulatedScrewdriver` owns the screw through one carriage state, changed
  only between ticks:
  - `Empty`.
  - `Suction`: held on the bit by vacuum.
  - `Welded`: an arm-owned search.
  - `Engaged`: held by the thread start on its member and turned by the process
    model.
  - `Threaded`: the SD13 helix.
  - `Seated`: SD13 after the seat.
- **What the MuJoCo acceptance exposed (2026-10-14).** Each is a modelling fix,
  not tuning:
  - **Velocity streaming yields under load.** `ServoSession` sent joint
    velocity targets, which SimKit realises as a proportional velocity loop
    with no load compensation, which is deliberate (`FLOW` is the
    load-compensated mode). The arm stalled at about 1 N against the flange,
    under the 2 N threshold. The search now streams `ServoPlan` chunks, as a
    force-controlled cell streams positions, so the drives' position loops
    push up to their ratings. `ServoPlanOptions` takes the cell's commissioned
    acceleration limits, the same as its planners.
  - **Free CAD bodies had no inertia.** Dynamic project parts were created
    with a mass but no inertial properties, so MuJoCo gave each 1 kg m^2 per
    axis. Every dynamic project part now carries its CAD centroid and inertia
    in its body frame.
  - **The feed end stop was soft.** The spring feed rests on its extended stop.
    MuJoCo's default limit (20 ms) let a release overshoot it by 1.9 mm, past
    the 1.1 mm overtravel, and the runtime faulted. `ScrewdriverSpindle` now
    declares a steel stop: 1 ms, critically damped.
  - **The simulated thread used the measured work.** The device's live work
    was the mission's registered estimate. It is now the part's true pose; only
    planning uses the estimate.
  - **Teeth are semantic.** Tapped-bore and screw hulls leave the screw free
    in the bore, and the process model's anchor is the thread start. The anchor
    now also catches a welded screw under the search. Anchored with a fixture,
    the screw is `Engaged` on its member, so its contact with the work is not
    tool load (406 N before the fix).
- **MuJoCo acceptance (2026-10-14).**

  | Case | Seated | Peak force | Searched surfaces |
  | --- | --- | --- | --- |
  | Nominal | 32.9 s | 0 N | 0 |
  | 1 mm offset | 34.7 s | 7.5 N (25 N bound) | 2: flange face, then plate |

  Both hand over to the unchanged qualified program, which ends OK at
  16.5 N m.

### SD13 the thread holds under load (2026-10-14)

The native reaction test was built and run for the first time.

What it exposed, layer by layer:
- **Inertia.** It created the spindle and screw without inertial properties.
  The MuJoCo backend gives such a dynamic body a nominal 1 kg m^2 per axis, so
  the 0.02 N m drive could not turn them. The test now states real inertias;
  CAD-built robots already do.
- **The thread coupling.** It then turned freely while the screw stood on the
  plate: the thread slipped 0.57 mm while carrying 0.17 N. MuJoCo scales a soft
  equality's impedance by the effective mass it acts on, here a 10 g screw, so
  the "ideal" coupling was a spring of a few hundred N/m. The contact was just
  as soft.
- **Chatter.** A stated stiffness (the coupling's spring path) on the bare
  screw chattered between 0.3 and 312 N. A 10 g body behind 1e7 N/m rings
  faster than the 125 us substep resolves.

The design that holds:
- The thread is a critically damped spring of commissioned axial stiffness.
- The screw slide carries armature: a tenth of the spindle's turning inertia
  reflected onto the screw axis (I / ratio^2). A rigid thread would add all of
  it; a tenth adds a tenth to what the spindle drive accelerates.
- The steel contacts take the stiffest stable time constant: two substeps.

Results at 1 ms and 2 ms steps:
- the torque-limited spindle stalls at 0.175 rad, against 0.157 rad to close
  its gap;
- the thread yields about 6 um, which is F/k;
- the plate carries the 63 N that 2 pi torque / lead predicts, within 25 %;
- the whole SimKit MuJoCo suite passes.

What changed outside the test:
- `rk_simulation_object_slide_desc` states the thread stiffness, damping ratio
  and slide armature.
- The simulated screwdriver derives the armature from the spindle's CAD
  turning inertia.
- A physical `screwEngagement` now requires `threadStiffnessNPerM` next to its
  axial-force cap.
- `checkScrewPhysicalThread` runs the whole flange on MuJoCo through the thread
  and requires the process model's qualified outcomes on the CAD seats.

### SD13 redesign: the thread joins the screw to the work (2026-10-14)

The first app run of the draft drove feed joint 0 to -22 mm (limit -20) at
14.6 s. The draft made the spindle the nut: its slide coupled screw travel to
spindle rotation on the tool. With a frictionless 1 mm lead, a 16.5 N m
tightening torque is about 100 kN of axial force, and the draft applied it
between the screw and the tool, so it pushed the tool back. A real thread
reacts between the screw and the tapped work. The socket transmits only torque,
and the screw is free to slide in it.

Design:
- **A helical joint in SimKit.** `NKSIM_JOINT_HELICAL` is a one-coordinate tree
  joint. Body b turns about `axis_a` and advances `lead` metres per revolution
  (signed, so a negative lead is left-handed). In MuJoCo it is a hinge, which
  is the joint's coordinate, plus a slide, held to `lead / 2π` per radian by
  the same thread spring the SD13 test qualified: commissioned stiffness,
  critical damping and slide armature.
- **The screw on the work.** `rk_simulation_create_object_screw_joint` puts the
  dynamic screw on a helical joint whose parent is the threaded member's body
  (a session object or a robot link), at the measured pose, on the CAD hole
  axis. The rotation range comes from the qualified run-down plus the final
  angle.
- **The socket.** A joint coupling from the robot's spindle joint to the
  helical coordinate (ratio = spindle-axis alignment; offset = measured) turns
  the screw. Axial position is not coupled: the bit and screw contact pair is
  already excluded, and the feed follows the advance as today.
- **Ownership.**
  - The physical thread carries engagement and run-down. The screw's axial
    position, and the reaction of a supported or loose workpiece, come from
    the solver.
  - The torque-angle process model keeps the tightening torque, friction,
    seat detection and results. The joint stays frictionless, so nothing is
    counted twice.
  - At the model's seat the carriage leaves `Threaded`. The screw is retained
    on its threaded member at the measured seated pose, and the final angle is
    turned on the retained pose by the process model. The frictionless thread
    never carries the clamp load, which would be about 10x the real preload.
  - Reverse runs the helix backwards to the lead-in, then regrips by suction,
    as the draft did.
- **Carriage.** The same `ScrewCarriage` state as SD12 (`Suction`, `Welded`,
  `Threaded`), with transitions only between ticks.

Checks:
- Native, both step sizes: the lead relation; the screw advancing into a
  supported plate as the spindle turns; a loose plate pulled up the screw
  against its support; and no axial force on the spindle link beyond the socket
  friction.
- App: `checkScrewPhysicalThread` seats all 4 screws with OK torque, keeps the
  feed inside its stroke, and matches the process-model mode's outcomes.

Results (2026-10-14):
- SimKit `a_helical_screw_turned_through_its_socket_clamps_its_seat` at 1 ms
  and 2 ms:
  - the screw runs down on its lead;
  - it seats after 0.314 rad, then the flank stretches by the clamp load over
    its stiffness;
  - the seat carries 2 pi torque / lead within 25 %;
  - the socket winds up about 1.4 mrad at the stall torque.
- RobotKit `screw_threads_into_its_member...`: threading measures without
  snapping; topology changes only while stopped.
- App `checkScrewPhysicalThread` on MuJoCo: all four CAD fastenings seat with
  the qualified OK result. It needed:
  - engagement where the process model's anchor is, at the entry within the
    lead-in, not anywhere within stroke range;
  - no wait for the Driving phase (the screw passes the entry during the
    approach);
  - CAD inertia on the screws;
  - the run-down torque limited to the program's limit and the thread's axial
    cap through the lead.

### SD15a design: one program per robot controller (2026-10-15)

Today one mission cannot pick, place and fasten:
- the validator only lets screwing share a mission with handling through a
  tool changer;
- a scene holds one `mission`, bound to one robot controller;
- the player resolves every tool against that robot's frames, and
  `robotTools` has no owner;
- `signal` writes only the mission controller's outputs.

Decision: **each robot controller runs its own program, and programs
coordinate only through wired cell signals.** A real cell works this way: each
robot controller runs its own program and handshakes over I/O, as the CNC
already runs its own program beside the robot mission (`CncProgramPlayer`).
The rejected alternative, steps that name an arm in one shared mission, has no
real controller behind it and couples two arms' planning into one sequence.

Steps:
- **SD15a.1 Schema (done, committed in `3bf6cca0c`).**
  - `mission` became `missions`, one per robot controller.
  - Every robot tool records its controller. One derivation,
    `SceneArtifact.toolController`, finds the controller that drives a joint on
    the tool's path to the assembly root (a changeable tool goes through its
    changer master). Validation checks the recorded owner against it, and
    generators fill it with `assignToolControllers`.
  - Each program is validated against its own tools. Screwdriver and torch
    limits are per controller.
  - A scene without modelled controllers is one robot with an implicit
    controller: one program, and tools without a controller.
  - SceneArtifact is v41; older ones are rejected.
  - ProjectKit tests cover:
    - two controllers' programs round-tripping;
    - another controller's tool refused;
    - two programs on one controller refused;
    - a tool claiming a controller that does not carry it;
    - two programs without controllers.
- **SD15a.2 Player (done, committed in `3bf6cca0c`).**
  - `ApplicationSimulation` runs one `MissionPlayer` per program. Each has its
    controller's robot, tools, screwdrivers and welders, feeders and blow
    feeds, and cell I/O.
  - `MissionPlayer` resolves only its own controller's tools.
  - `missionPlayer(controllerId)` names a program; `missionPlayer()` stays
    the accessor for single-program cells.
  - Retry resets the failed program's robot.
  - The editor's mission panel follows one program and offers a selector
    when there are several.
- **SD15a.3 Cell.** A pick, place and fasten example beside the screwdriving
  cell:
  - **Handling robot.** A second `RobotArm` with its own controller carries
    the MT12 dual gripper (`DualArmGripperTool`). Gripper A is sized to the
    flange housing and gripper B to the tapped plate, as commissioned part
    widths (`ParallelGripperSpec`).
  - **Free parts.** The plate and the housing are free parts. The fixture
    stops locate the plate, and a presence sensor confirms it is seated.
  - **Trays.** MT9 pocketed trays with presence sensing: an infeed tray holds
    plates and housings, and an outfeed tray takes finished assemblies.
  - **Handling program:**
    1. Pick the plate (B) and place it in the fixture.
    2. Wait for plate-present.
    3. Pick the housing (A) and place it on the plate.
    4. Signal `part-ready`.
    5. Wait for `fastened`.
    6. Pick the fastened assembly by its plate (B) and place it in the
       outfeed slot.
  - **Screwdriving program:** wait for `part-ready`, fasten the four CAD
    screws from presenters or the blow feed, then signal `fastened`.
  - **Fastened assembly in simulation.** Screws and housing are retained on
    the plate when fastened, so gripping the plate carries the whole assembly.
    This needs the plate to be a dynamic carrier for retained bodies.
  - **Wiring.** Handshakes are wires between the two robot controllers' I/O,
    declared in CAD with `connectPorts`.
  - **Order of work:**
    1. The cell CAD and controllers.
    2. Both programs with the plate fixed and only the housing handled.
    3. The plate handled and the unload.
  - **Constraints found in the code (2026-10-15):**
    - The fastening analysis (`FastenedAssembly`) derives the CAD screw seats
      from the flange seated on the plate, so the `flange-seat` mate stays in
      the design.
    - The free housing follows the screws' pattern instead: a dynamic part
      that the runtime stages at its supply (here the infeed slot), with
      planning still using the designed seat.
    - The bearing is a separate occurrence inside the housing, so it must
      travel with it as one rigid body. Either the bearing becomes a fixed
      member of the housing's body, or the free part is the flange
      subassembly as a whole.
    - **Decision:** `dynamicParts` are per occurrence, so a housing listed as
      dynamic would leave its bearing behind. The SD15a part is the housing
      before its bearing is fitted, as lines that fasten housings before a
      later press station do. It is sized from the same bearing, with the
      same CAD fastenings. Free rigid subassemblies (one dynamic body from a
      subtree's rigidly joined members) are a separate, general feature, not
      needed here.
    - `ControllerWiring` requires every motor in a cell with a cabinet to be
      wired to one. Both arms get a `RobotController`, each wired to its six
      drivers. The screwdriver tool declares no motors, so it needs no
      cabinet.
    - The gripper valves and air go to the handling controller and an air
      supply.
- **SD15a.4 Checks.** On both backends:
  - a full tray-to-finished-assembly cycle;
  - fixture not ready;
  - a missing or misplaced part;
  - screw supply failure;
  - an interrupted fastening, with resume and recovery.

### SD15 machine-tending interface audit (2026-10-13)

MachineKit already has CAD-side `ToolChangerMaster`, `ToolChangerTool` and

signal ports and can build one static robot/tool assembly configuration. The
RobotKit also has a lower-level `EndEffectorRuntimeBridge`, `ToolRuntimeSelection`

collision geometry, TCP or capabilities while the robot runs.

The current SD15 source draft extends `ToolRuntimeSelection` with an explicit
process lease: outputs require the owning process, and selection is rejected
while that process still owns the tool. Selection also rejects a configuration
whose changer does not share the active lock or whose lock does not report
engaged. The current follow-up replaces the bare lock boolean with a timestamped
observation containing measured mounted-tool identity, lock state, source clock
and acquisition time. Selection checks the expected tool ID, rejects clock
mismatch and future observations, and the simulation models attach/detach while
unlocked. Tool outputs are initialized safe on selection, and a process cannot
release its lease while any declared output remains unsafe. Regressions cover
wrong identity, clock/time ordering and unsafe lease release. Compiler-only
checks pass; focused runtime checks for this follow-up are pending. The
remaining runtime boundary must connect lock commands to fresh measured cell
feedback, attach and detach the CAD tool geometry, and preserve the exact mount
and process state on interruption. The cell should reuse MT8/MT9 geometry and
MT6/MT7 signals; adding multiple `robotTools` records or choosing a static
`EndEffectorSet.configuration` alone does not model that exchange.

### SD15 process-ownership follow-up (2026-10-13)

`ToolRuntimeSelection` already routed process outputs and tool sensor frames
per selected end-effector, but a caller could switch configurations while an
outgoing process was still active. The draft now gives one named process an
exclusive lease on the selected tool, routes owned output events explicitly,
rejects unowned or mismatched writes, and refuses tool selection until the
owner releases the lease with every declared output at its safe value.
Configuration selection initializes its declared outputs to those values.

unlocked. Compiler-only checks pass for 1,741 RobotKit sources and 1,804
