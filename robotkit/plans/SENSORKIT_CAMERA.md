# SensorKit camera source: Phase 7 spike decision

**Decision: conditional go for a simulation sensor source.** The prototype rendered a
SceneKit emissive triangle through `SceneCameraAdapter`, encoded it as SensorKit's
HMPK `PackedFrameMessage`, decoded it with the generated Haxe record, converted
RGBA8 to RobotKit `rgb8`, and submitted it to the Phase 4 ONNX detector. This
establishes a viable in-process simulated camera path. It does not establish a
headless, windowless renderer or a production integration.

## Evidence and measurements

- The native prototype lives in `sensorkit/sensor_render/tests/sensor_render.cpp`.
  Set `NKSENSOR_CAMERA_SPIKE_OUTPUT` to write its captured HMPK frame. The
  committed 16×16 fixture was generated by that test; the Haxe end-to-end check
  is `robotkit/tests/src/tests/spike/SensorkitCameraSpikeTests.hx`.
- On this Linux host, configure with `NKSENSOR_BUILD_SIM=OFF` took about 5.5 s;
  the first Ninja build had 183 steps and its Ninja log shows about 10.9 s of
  build time with ccache and eight jobs. These are warm host figures, not a
  portable clean CI estimate. The render dependency pulls in SceneKit scene and
  scene_render, NativeKit GPU/window, and libwebsockets. It does not require
  CadKit or OCCT.
- Twenty repeated 16×16 software-rendered captures under `xvfb-run` and
  `LIBGL_ALWAYS_SOFTWARE=1` averaged **0.138 ms per capture** on this host.
  This is a tiny frame and excludes ONNX inference and Haxe conversion. The
  generated HMPK frame is 1,077 bytes. An optimized C++ loop copying RGBA8
  to RGB8 at 640×480 took 0.202 ms per frame over 1,000 passes on this host.
  This is a lower bound, not the Haxe adapter cost. A full resolution Haxe
  benchmark remains necessary before throughput claims.
- The test runs headless under Xvfb, but still creates a NativeKit window and
  GPU surface. The center pixel was RGBA `(255,31,31,255)` with software GL;
  the pre-existing test's strict `<20` nonred threshold had to be widened to
  `<40`. A truly windowless CI path is unproven.

## Conversion choices and constraints

- The spike strips alpha to `rgb8`: the detector currently accepts only `rgb8`,
  and adding `rgba8` to RobotKit would still require a conversion at inference.
  This copies 3 bytes per pixel after the wire decoder's payload copy and the
  immutable `CameraImage` constructor's copy. Measure at target resolutions and
  reduce copies before a production path.
- The numeric SensorKit sensor ID must have an explicit mapping to a stable
  string ID present as a camera in `RobotModel.sensors`. Unknown IDs fail.
  SensorKit's numeric frame ID is not treated as a RobotKit model frame ID;
  the mapped model sensor supplies its mount frame.
- Capture and delivery times both originate in simulation seconds. They become
  nanoseconds with `sensorkit.sim` clock IDs for source and received time. The
  adapter never labels delivery time `robotkit.monotonic`. Crossing to robotd
  would require an explicit `ClockMapping` or a new host receive timestamp.
- SensorKit's generated Haxe codec validates required fields but does not by
  itself enforce camera type, pixel format, packed stride, payload length, or
  reasonable image dimensions. The conversion point does those checks.

## Production work

Move the mapping into a configured robot/sensor bridge, define how SensorKit
numeric IDs are allocated and persisted, and connect a simulation scheduler to
SensorKit's capture/delivery lifecycle. Add full resolution latency and memory
benchmarks, a windowless renderer or CI display contract, loss/queue behavior,
and tests across the intended GPU drivers. Keep the wire dependency isolated at
one adapter and use explicit clock mappings for any cross-process timing.
